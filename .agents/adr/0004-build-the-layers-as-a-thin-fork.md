# Build the five layers as a thin fork

The SRD adds five layers (Foundation, Autopilot, Review, Guardrails, Discovery) on top of the upstream skills, and requires that the monthly upstream merge stays a small, routine job (G4, N3). We built every layer as new skill folders, new files inside upstream skill folders, and a handful of small, logged edits to upstream `SKILL.md` files. Several of the choices below would look odd without the reasons, so they're recorded here.

## Decisions

- **`/ship` owns its own per-ticket loop instead of calling `implement-spec`.** Both are user-invoked, and the invocation rule forbids one user-invoked skill from calling another. `implement-spec` stays user-invoked (it is a supervised command, SRD G5), so `/ship` carries the unattended version of the loop in `RUN-LOOP.md`, adding parking, the ledger and the autonomy contract. `implement-spec` keeps a compact supervised version. Both use the same step names (implement, spec review, quality review, fix, verify, commit) so the two stay recognisably one loop.
- **Discovery and red-team are inlined in `/ship`**, for the same reason: the three pm-skills ports are user-invoked (they must never auto-trigger and compete with grilling), so `/ship` carries a condensed copy in `DISCOVERY.md`. The standalone skills save a file `/ship` can start from.
- **`to-spec` and `to-tickets` became model-invoked, with narrow descriptions.** `/ship` must chain them. Their descriptions name the only two triggers (an explicit request, or `/ship`'s step), so they don't fire during casual design talk; the trigger evals check that.
- **`brainstorm` is model-invoked but scoped to `/ship`.** A harness can only let one skill call another if the callee is model-invoked, so "no auto-trigger" is achieved through the description, not the frontmatter.
- **One `stack-review` skill with on-demand checklist files, not one skill per stack.** Every model-invoked skill's description is loaded into every session (N1). Per-stack skills would each add a description; one skill with a file per stack costs one description and loads only the checklists a diff touches (Q1's "others add no context cost").
- **Commands and known failures live in `docs/agents/commands.md` in a strict bullet shape.** The skills and the hooks need the same commands (F1: none hard-coded). A Markdown file keeps it beside the other `docs/agents/` config and readable by people; the fixed `- **key**: \`command\`` shape lets the bash hooks parse it without a JSON or YAML dependency.
- **Hooks ship in `hooks/hooks.json`, auto-loaded by the plugin.** Claude Code loads that default location without a `hooks` entry in `plugin.json` (verified on 2.1.296), so the manifest doesn't declare it. The stop guard is opt-in per run through the ledger, and releases a session after three blocks with an unchanged ledger, so a stuck run can't trap a session forever.
- **The command allowlist is enforced by a hook, not just the prompt.** SRD N6 forbids running commands outside the allowlist agreed in preflight; an unattended agent that forgets an instruction can't be allowed to forget that one. `hooks/allowlist.sh` reads the run's contract and refuses anything else while a run is `running`, plus the hard rules (no push or merge to main, no force push, no branch deletion). The contract's backticked entries are the machine-readable allowlist.
- **`.ship/` is ignored through `.git/info/exclude`**, not `.gitignore`, so starting a run doesn't leave an uncommitted change in the user's repo (N7). A team that wants run history committed opts in through `docs/agents/autonomy-contract.md`.
- **Upstream syncs apply a patch rather than merge.** This repo's history starts at a snapshot of upstream `v1.3.1`, so there is no shared history to merge on. `scripts/upstream-sync.sh` applies upstream's delta since the recorded baseline with a three-way apply, and `FORK-CHANGES.md` lists what to replay on conflict.

## Consequences

- A change to the per-ticket loop has to be made in two places (`ship/RUN-LOOP.md` and `implement-spec/SKILL.md`), and likewise for discovery (`ship/DISCOVERY.md` and the three productivity skills). The duplication is accepted as the price of the invocation rule.
- Upstream edits to `to-spec`, `to-tickets`, `implement-spec`, `grilling`, `code-review`, `pr`, `setup-keelwork` and `ask-keelwork` will conflict on sync. Each conflict has a row in `FORK-CHANGES.md` saying what to replay.
